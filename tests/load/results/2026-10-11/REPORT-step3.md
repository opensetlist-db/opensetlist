## What the drills say

- **Total loss of the warm cache (`absent`, `getnull`, `seterror`, `setskip`, `geterror`) degrades to the warming-OFF R2 on Small and nothing worse**: save→visible p95 1.85–2.29 s (step 2 with warming: 1.67 s), per-save builds roughly double (≈ 400 vs 163–227 per PUT rev), the backend pool is saturated for ~1 s per save, Σ 115–170 of the 400 cap, 0 missing, 0 × 5xx. Individual clients cross 3 s in the storm (max 3,032–3,614 ms; 1–3 of 4,000 per drill), the p95 does not. `setskip` is the SDK's swallowed-write shape (`ok=true`, entry absent): nothing distinguishes it from `absent` on the read side except the `set` lines claiming success — the hit rate is the only honest signal, which is why the runbook's T−10 check reads `x-snapshot-source`, not the writer's log.
- **Partial publication (`locale=ja` / `locale=en`)**: the missing locale takes the storm, the others stay warm; ja (~70 % of the traffic) missing gives pairs p95 1,638 and backend 16 busy; en missing is nearly invisible (p95 1,631, backend p50 3). SDK gates pass in both.
- **Slow cache (`slow=150`, `slow=400`)**: +150 ms per lookup costs ~150 ms of p95 (1,826 vs 1,671) with 99.5 % hits and 35 real timeouts (150 ms + the cache's own tail crosses the 300 ms deadline occasionally); +400 ms trips the deadline on 56 % of lookups (`timeout` 3,590) yet one third still hit — finding 2 — and p95 is 2,029.
- **Slow warm job (`slowjob=1000`)**: every hinted fetch of a save lands within ~0.5 s of the broadcast (e.g. rev 1240: 327 lookups between +0.0 and +0.5 s), the three-locale job takes ~2.3 s (`done ms=2344`, `LIVE_WARM_CONCURRENCY=1`), so 98.7 % of lookups miss and the readers rebuild: p95 2,111, pages p95 2,517. Warming only pays when the job publishes within ~300 ms of commit; step 2's jobs took 77–300 ms, i.e. the budget is real and thin. Also visible: in a pair, the insert's job (started 1 s late) built the PUT's content and stored it under the insert's key (`atLeastRev=1239 rev=1240`) — correct at-least semantics, but useless to clients hinted with 1240.

## Findings

1. **`locale=ja` save 6 (rev 1111, standalone): pages gate FAIL at p50 3,130 / p95 3,178 ms — a load-host browser stall, not the fault.** All 30 pages' hinted fetches for that save took 2.3 s (p50 2,323, p95 2,621) **regardless of snapshot source** — `cache` 2,323, `warm` 2,379, `build` 2,323 — while the 450 SDK clients' hinted fetches for the same save took p50 594 / p95 802 ms and the server's lookups were normal. A warm or cache hit is answered in tens of milliseconds; 30 pages waiting 2.3 s for it in lock-step points at the Chromium process (one browser, 30 pages), which the step-1 validity monitors do not cover (they watch the harness's Node threads: main lag max 570 ms in that run). The other 7 saves of the drill: pages p50 1,000–1,447, p95 1,216–1,706. **The verdict stays VALID + FAIL as the gate is written.** The drill was re-run once 56 minutes later on the same deployment (`locale-ja-2`): VALID + PASS, pairs p95 1,598, pages p95 1,629 (per save p50 953–1,437, p95 1,211–1,658), SDK p95 1,597, max 2,030, warm 33.1 %, same fault evidence — the stall did not recur and the first run's numbers stay in the record. The follow-up is a page-side stall detector: hinted fetches for a save that return `warm`/`cache` in ≥ 80 % of pages but take > 1 s on all of them = browser stall → pages verdict INVALID, SDK verdict kept. Same family as step 2's 42-client SDK tail (1.8 s on one instance) in that the load host's own process is the suspect, with the difference that here the evidence is direct.
2. **`slow=400` is not a 0-hit mode: same-key coalescing lets late joiners hit.** The 300 ms reader deadline is per request; the slow `get` is shared by every lookup of the same key in flight. A lookup arriving 150 ms after the first one sees the `get` resolve 250 ms later — inside its own deadline — and hits. Under a 500-viewer burst that is a third of the lookups (2,072 hit / 3,590 timeout / 706 memo-miss). The README table ("never warm") was written for a lone request; the code is right, the doc is wrong — fix the README row to "first lookup per key per instance `timeout`, coalesced followers may `hit`". Three repair rev-reads (`x-snapshot-source: repair`) also appeared only here.
3. **`geterror` floods the error log**: 1,623 `lookup-error` lines in four minutes (one per failed `get`). Harmless to the gate, but a real Runtime Cache outage during the show would bury every other error. Follow-up: rate-limit the `lookup-error` line per instance (first occurrence + one per 10 s with a count). `seterror` writes 54 `set-error` lines (3 per save) — fine.
4. **Real cache tail latency exists without a fault**: `getnull` (normal `get`, value dropped) had 1 `timeout` in 6,304 lookups and `slow=150` had 35 in 7,250; step 2 had 0 in 10,459. The 300 ms deadline is adequate; the reader's `timeout → build` path is exercised in production occasionally and behaves.
5. **Harness: `--strict-host` refusal crashes on Windows on the way out** (`Assertion failed: !(handle->flags & UV_HANDLE_CLOSING), file src\win\async.c, line 76`, exit 0xC0000409 instead of 2). The refusal and its clean-up complete first, nothing is created — observed on the first (pre-fix) attempt `browsers-fault-absent-strictcheck.*`. Follow-up: close the worker/CDP handles before `process.exit(2)`.
6. **Cold-start hypothesis for the 1.8–2 s tails** (from the deployment verification, not the drills): the first requests to a fresh deployment took 2.0–2.4 s; under a burst Fluid spins up extra instances and the requests routed to one pay its cold start. Step 2 Session B's 42 clients on one instance for 1.8 s fits. For step 5 (cold admission).

## Acceptance statement for sustained outages

If the Runtime Cache is absent, failing, silently dropping writes or over the 300 ms deadline for the whole show, R2 on Supabase Small behaves like the qualified warming-OFF R2: save→visible p95 1.9–2.3 s at 500 warm viewers, 0 missing, 0 × 5xx, the backend pool saturated for ~1 s per save, Σ ≤ 170 of 400. **This degraded mode is accepted for the Fes** on three conditions: (a) the fleet is warm — the Small control showed a cold fleet answering a 500-burst with 12 % HTTP 503 without warming, so the pre-show warm-up and the step-5 cold-admission result, not this step, cover doors-open; (b) the T−10 operator save check reads `x-snapshot-source` on all three locales and a non-`warm` answer puts the operator in "degraded mode" (expect ~2 s, watch the backend pool, no deploys); (c) **a 503 during the show is a gate failure and is recorded as one — retries that eventually succeed do not satisfy zero-5xx.** Partial-locale and slow-job faults are covered by the same statement with better numbers. Not covered by this step: cache faults during admission (step 5), overlapping jobs (step 4), ON↔OFF transitions (step 6).

## Harness and doc follow-ups

Page-side browser-stall detector (finding 1); README `slow=400` row (finding 2); `lookup-error` rate limit (finding 3); `--strict-host` exit path on Windows (finding 5); `warm-join` "arrived after warm-complete" should key on the hinted rev's own entry, not any entry carrying that content (`slowjob` showed 49 % "after" with 0 % hits because the insert's late job published the PUT's content under the insert's key).
